# 想法收集箱（Backlog）

> **用途**：记录"想到了、但暂不实现"的点。**不塞进 V1.0，也不丢。**
> **规则**：每条写清 ①想法 ②为什么暂不做 ③什么时候做。
> **为什么要有这个文件**：避免每个新想法都变成一次需求变更，拖慢当前版本；同时保证好想法不会遗忘。
> 创建：2026-10-09 · 由项目负责人提出

## 一、数据建模类

### 1. 辣度的可变性 ⭐
**想法（2026-10-09）**：辣度分两段——**基础辣度** + **可加辣**。有的菜天生带基础辣度（水煮肉片、麻婆豆腐），有的没有（清汤面、沙拉），但**两者都可以再加辣**。

**为什么暂不做**：需要菜品端多一个字段 + 打分逻辑多一个分支；而且 V1.0 里不做**不会导致推荐出错**，只是不够精准。

**什么时候做**：V2.0（有数据库后，和下面的第 2 条一起做）

> **补充（2026-10-09，第三次撞到同一概念）——口味的"双重角色"**
> 项目负责人在写 `scoreDish()` 时提出：口味这个字段很尴尬，**既是"喜欢"（加分项），又是"限制"（过滤项）**；在菜品端**既是"固定属性"（麻婆豆腐必辣），又可能是"可调变量"（麻辣烫可选清汤）**。
>
> 这解释了一个 **V1.0 的真实边界**："不能吃辣"这个输入在 V1.0 **没有优雅的处理方式**——
> - 填进 `avoidHard` → **过度剔除**（连可换清汤的麻辣烫一起剔掉）
> - 填进 `taste` → **只是加分**（辣的菜仍然可能出现）
>
> 这个边界在 V1.0 **可以接受**：先让最简单的打分跑通，等 V3.0 交给大模型去理解"这道菜辣度到底可不可调"。
>
> ⭐ **同一概念被独立想到三次**（辣度可变性 → 属性可替换 → 口味的双重角色），说明它是这个项目的**核心建模问题**，不是边角料。V2.0 设计数据库时应优先回看这一组条目。

### 2. 属性的"可变性"标注（removable）
**想法（2026-10-08）**：区分"麻辣烫可换清汤"与"麻婆豆腐必辣"。菜品需要标注**哪些属性是可以调整的**。

**为什么暂不做**：V1.0 只有 12 道菜、标签还很粗，手工标注准确性低。

**什么时候做**：V2.0（`ingredients` 表 + `is_removable` 字段）

> 📌 **1 和 2 是同一类问题的两个实例：属性的可变性。** 同一个概念被独立想到两次，说明它是真问题。

### 3. 静态属性 vs 动态属性（建模分类）
**想法（2026-10-09）**：属性不该混成一类，至少要分三层：

| 类型 | 例子 | 特点 |
|---|---|---|
| **菜品固有属性**（静态） | cuisine、calories、heaviness | 这道菜本身就是这样，不随点单变 |
| **点单可调属性**（半动态） | 辣度、香菜、份量、加不加葱 | 下单时可以调整 |
| **环境相关属性**（动态） | 价格、能买到什么 | 随地域/时间/供给变化 |

**为什么记录**：这个分类会直接影响 V2.0 的表设计——**第一类进 `dishes` 表，第二类要进关联表（如 `dish_options`），第三类是数据源问题、不进模型**。

**什么时候用**：V2.0 设计数据库表时回头看这一条。

### 4. 价格的地域浮动
**想法（2026-10-09）**：同一道菜在成都和上海价格不同；现在是静态参考价。

**为什么暂不做**：需要一个真实的价格数据源，V1.0 不具备。

**什么时候做**：V3.0，甚至可能永远不做（成本高、收益低）

## 二、推荐机制类

### 5. 多推荐（3 道 + 1 道惊喜）
**想法（2026-10-08，WP 提出）**：一次推 3 道常规 + 1 道惊喜，让用户自己选。

**为什么暂不做**：需要新的 UI（卡片列表）；V1.0 的滚动动画天然适合"单道结果"。

**接口现状（2026-10-12 修正）**：设计文档里规划过 `alternatives: []`，但 **V1.0 的实现里并没有落地这个字段**。V2-E 改造时直接改用新结构，**不需要兼容旧的返回格式**。

**接口改造方案（2026-10-12，项目负责人提出）**：

- **现状**：V1.0 的 `onRecommend` 复用单卡片 UI，一次只出一个菜
- **期望**：改成「Top 3 列表 + 1 个惊喜菜品」
- **触发时机**：**V2-E 前端接入联调时**，配合 `fetch` API 一起改造
- **接口改造**：`/api/recommend` 的返回结构从单对象改为 `{ top: [...], explore: {...} }`

**什么时候做**：**V2-E**（不再是 V1.5 —— 因为改接口的最佳时机，正是换后端的那一次）

### 6. 动态调权（根据历史反馈调整权重）
**想法（2026-10-08）**：用用户的选择历史去调整各维度权重，**带上下限**防止某一维跑偏。

**学名**：基于反馈的权重学习（contextual bandit 的简化版）。**这个词可以写进考研复试材料**——系统根据反馈自适应，正是"复杂自适应系统"的典型特征。

**什么时候做**：V3.0

### 7. 用户自定义权重
**想法（2026-10-08）**：让用户自己决定"口味 vs 健康"哪个更重要。

**注意**：实现方式不是"额外加 20 分"，而是**调权重**（比如一个滑块）。因为"加分"本质上就是在改权重，只是写法不统一。

**什么时候做**：V3.0

### 8. 相对均衡（健康维度的落地方式）
**想法（2026-10-08）**："健康"和"营养均衡"无法精确量化，改为以**相对均衡**为目标：不看精确比例，只看"不极端"——连续几天高热量，就推低热量的。

**依赖**：历史数据（`history` / `pick_history`）

**什么时候做**：V3.0

## 三、工程优化类

### 9. 抽取池缓存（原 `pickPool` 变量的意图）
**想法（2026-10-09）**：把过滤后的候选池缓存起来，避免每次抽取都重新计算；菜单变化时（增删菜品）清空缓存。

**来历**：`index.html` 里原本有一个 `let pickPool = []` 变量，在 `addDish` / `removeDish` 里被重置，但**从未被读取**——是一个没写完的实现残留。经全文检索确认（3 处引用，全是写入，零读取）判定为死代码。**删除前把它的意图记在这里，代码干净了，想法不丢。**

**为什么暂不做**：V1.0 只有 12 道菜，重算一次候选池的成本约等于零，缓存带来的复杂度远大于收益。

**什么时候做**：V2.0 数据量上升后，如果发现过滤成为性能瓶颈再考虑。**很可能永远不需要。**

## 四、产品与发布类

### 10. UI 自定义（主题色 / 背景）
**想法（2026-10-09）**：在设置界面里让用户自定义背景、配色等外观。

**技术前提已经具备**：`index.html` 的 `:root` 里已经用 **CSS 变量**定义了主题色（`--bg` / `--card` / `--accent`）。改这些变量的值就能整体换肤——这正是主题切换的标准做法。

**为什么暂不做**：对投简历的价值低（面试官不会因为能换主题色加分）。

**什么时候做**：V3.0 之后或任意间隙。它**独立于核心链路**（不依赖 `recommend()` / `store()`），什么时候插进去都不会打乱节奏。

### 11. 响应式布局（手机上能正常看）⭐
**想法（2026-10-09，HP 建议）**：这是投简历时真正"看得见的亮点"之一——面试官很可能用手机点开你的链接。

**现状**：页面有 `viewport` meta，但 `.wrap` 固定 `max-width: 640px`，小屏下偏好面板的多列布局会挤在一起。

**什么时候做**：**T5 之后、V2.0 之前**，成本约 1 小时。

### 12. 部署上线（有一个可访问的链接）⭐⭐
**想法（2026-10-09，HP 建议）**：投简历时"**有一个链接**"的价值，远高于"我在本地跑通过"。

**现状**：`HANDOFF.md` 记录 GitHub Pages 未开启（`has_pages: false`），Gitee Pages 已停服。

**前置条件**：
- V1.0 是纯前端 → 可直接部署静态站点（GitHub Pages，3 分钟）
- V2.0 有后端后 → 需要一台云服务器或 Serverless 平台

**什么时候做**：**V1.0 验收通过后马上就能做**——开个 Pages 就行。

## 五、使用建议

- **想加需求时先问一句**：*"V1.0 不做这件事，会不会导致 V1.0 做错？"*
  - **不会** → 写进这个文件，继续手头的活
  - **会** → 那才是真需求，改设计文档
- 这个判据能挡住 90% 的"需求膨胀"，同时不丢掉真正的洞察。
