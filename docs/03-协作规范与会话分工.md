# 协作规范与会话分工

> 日期：2026-10-07 · 起草：HP
> 用途：规定多会话协作时**谁改什么文件、怎么交接、怎么不发生冲突**

---

## 1. 为什么会话不能随便开

一个人同时管理多个 AI 会话，会遇到三个真实问题：

1. **上下文断裂**：开发会话不知道设计细节，会自己发明字段名，和设计文档对不上。
2. **文件冲突**：两个会话同时改 `index.html`，后写的覆盖先写的。
3. **决策分散**：每个会话都会问你问题，最后你记不清哪个已经拍板过。

所以下面的规则不是形式主义，是防止你返工。

## 3. 文件锁规则（最重要的一条）

> **同一时刻，一个文件只能有一个会话在改。**

| 文件 | 当前所有者 | 说明 |
|---|---|---|
| `index.html` | 🖐 项目负责人（V1.0 期间） | HP 不代写；开发会话只做答疑 |
| `docs/00-需求终稿.md` | HP | 冻结后要改需走变更记录 |
| `docs/01-设计终稿.md` | HP | 契约变更必须由 HP 修订 |
| `docs/02-V1.0任务卡.md` | HP | 可追加答疑记录 |
| `config.local.js` | 🖐 只有你 | 任何人不得读取/写入 |
| `db/**` | 🖐 **DB 会话**（B 阶段） | `schema.sql` 与种子数据；其他人只读 |

| `backend/**` | 🖐 待定（V2-C 开工时指派给开发会话） | DB 会话只读 |

**如果两个会话都要改同一个文件**：先让一个停下来（在会话里说"暂停，等另一个改完"），改完提交，另一个再 `git pull` 后继续。

## 4. Git 规范

### 4.1 分支策略（单人项目从简）

```
main          ← 稳定可运行，只接受合并
└── feat/v1   ← V1.0 开发分支
└── feat/v2   ← V2.0 开发分支
```

**简单做法**：小改动直接在 `main` 上做也行，但**每完成一个任务就提交一次**，别攒一堆再提交（出问题无法回退）。

### 4.2 提交信息格式

```
feat: 新增偏好面板（地域/口味/心情）
fix: 修复预算过低时推荐返回空
docs: 补充 V1.0 任务卡
refactor: 抽取滚动动画为公共函数
```

### 4.3 推送（双远程，推两次）

```powershell
git add .
git commit -m "feat: xxx"
git push            # GitHub (origin)
git push gitee      # Gitee
```

⚠️ **注意**：本会话（HP）在受限权限下**无法执行 `git push`**（ssh 建不了内部管道，报 Win32 error 5）。推送需要你**在自己的终端手动执行**，或者临时把会话切到「完全权限」。

### 4.4 提交前安全检查（每次必做）

```powershell
git status                              # 不能出现 config.local.js / .env
git diff --cached | Select-String "sk-"  # 暂存区不能有 key
```

如果 key 已经误提交过：
```powershell
# 立刻去 platform.deepseek.com 吊销该 key，重新申请一个
# 然后清理历史（这一步复杂，届时找 HP 帮你做）
```

## 5. 交接机制（六项）

每张任务卡/每次会话交接，必须写清这六项：

| 项 | 含义 | 举例 |
|---|---|---|
| 1. 目标 | 做完之后什么变了 | 「菜品数据结构升级为 v2」 |
| 2. 输入路径 | 从哪里读 | `index.html:131-167` |
| 3. 输出路径 | 写到哪里 | `index.html` 同区块 |
| 4. 决策点 | 需要拍板的地方（二选一 + 推荐） | 「旧键删不删 → 推荐不删」 |
| 5. 验收标准 | 怎么算做完 | 「清空 localStorage 后刷新，12 道菜都在」 |
| 6. 成本预估 | 大概要多久 | 1.5–2 小时 |

**模板**（开新会话时复制这段给它）：

```
你是本项目的【开发会话】。请先读这三个文件再动手：
- D:\projects\today-eat-what\docs\00-需求终稿.md
- D:\projects\today-eat-what\docs\01-设计终稿.md
- D:\projects\today-eat-what\docs\02-V1.0任务卡.md

本次任务：<任务卡里的 T? 编号 + 标题>
输入路径：<...>
输出路径：<...>
验收标准：<...>

约束：
1. 遵守 01-设计终稿 的接口契约，字段名不得自创
2. 不要动 docs/ 下的设计文档
3. 改动前先说明你打算改哪几行，等我确认
4. 不要用 PowerShell 的 Get-Content/Set-Content 改中文文件
```

## 9. 带教规范（HP 的工作方式）

> 由项目负责人于 2026-10-09 提出：**"以后指导前先给一个目标、解释或框架，让我知道这是做什么、有大致概念；末尾再复盘。"**
> 这是一个合理要求，**从 T3 开始执行**。

### 9.1 每个任务按四段给

| 阶段 | HP 要给的 | 目的 |
|---|---|---|
| **动手前** | 【目标】这一步要达成什么<br>【为什么】它在全局哪个位置、不做会怎样<br>【做什么】具体动作 | 建立**地图**，避免"跟着抄却不知道在干什么" |
| **动手时** | 你写，HP 只答疑、不代写 | 长手感 |
| **动手后** | 【复盘】预期 vs 实际、踩到的坑、学到的概念 | 把"做过"变成"懂" |

### 9.2 三条硬要求

1. **先给地图再给路。** 不许一上来就甩代码，必须先说这一步在整体流程里的位置。
2. **概念要落地到本项目。** 不许只讲抽象名词，必须说"在你这个项目里，它就是……"。
3. **复盘要基于事实。** HP 必须**实际读代码**再评价，不许凭对话印象夸奖；发现问题直说，**包括 HP 自己的错误**（2026-10-09 已发生过一次：HP 把 AI 写的代码当成负责人写的来表扬）。

### 9.3 关于"抄代码"

- **允许抄**，但抄完必须能回答一句："这段是干什么的？"
- 抄来的代码里，出现 `!= null` / `??` / 显式判断的地方要**特别留意**——那通常是别人踩过坑留下的记号。
- 区分两类代码：**一次性的**（如迁移函数，跑完就不再动）可以不求甚解；**要反复改的**（如打分函数）必须真懂。

### 9.4 阅读代码的习惯（2026-10-09 补）

读到看不懂的写法时，别放过——**在浏览器控制台亲手敲两种写法，看结果差在哪**。这比读十遍解释都有用。

### 9.5 答疑方法（2026-10-13 补）

**答疑的难点是定位，不是解释。** 完整方法与出题设计见 `14-答疑方法与出题设计.md`（**断点定位法**）。三条最小要求：

1. **先复述对方已经想到的那几步**，确认他的路线没歪——不要一上来就讲。
2. **判断断点是「点」还是「面」**：「点」是空的（没见过）就直接补点；「面」是断的（两个都懂的知识之间那根线没连上）就补联系。**从断点往下讲，绝不从头上讲。**
3. **补面**：把这个知识点在本项目里还出现的同类位置一次列全，把一个点变成一张网。

## 10. 分界线原则：一件事该谁动手（2026-10-13 新增）

> 由项目负责人提出：「涉及重复性的、学习价值弱的、之前做过的，就 DSH 直接做，只需要说明即可；相反的，留下提示、告知我，并一步步指导我。」
> 用途：V2.0 之后不再"全程手动粘贴"，但也不放养成"全交给 AI"。

### 10.1 唯一判据

问一句：**这件事不做，我会不会学不到东西？**

| 情形 | 谁做 | 例子（本项目） |
|---|---|---|
| 学习价值高 · 第一次做 · 要拍板 | **项目负责人亲手做**，AI 给地图 + 一步步指导 + 事后复盘 | ER 图的基数判断、表关系设计、第一次写 FastAPI 路由、`store()` 换实现 |
| 学习价值弱 · 重复性 · 之前做过 | **AI 直接做**，动手前一句话说明，动手后给证据 | SQLite→MySQL 语法转写、批量插 12 道菜、目录迁移、格式统一、跑回归测试 |
| 判断不了 | 按"学习价值高"处理（宁可多教一次） | — |

### 10.2 三条护栏（防止"直接做"变成"静默乱做"）

1. **不许静默**：AI 直接做之前，必须一句话说清「我要改哪个文件、改什么」，做完必须给可验证证据（文件路径 + 命令输出 + 行数/结果）。
2. **随时可收回**：项目负责人任何时候说「这个我要自己做」，AI 立刻停手改成指导模式。
3. **不可逆动作一律先确认**：删除、覆盖、写库、`git push`、改表结构——**即使学习价值低，也要先拿到明确同意**。这条优先于 10.1。

### 10.3 应用到 V2.0（当前分工）

| 段 | 谁做 | 依据 |
|---|---|---|
| B-2 ER 图 | 负责人核基数（DB 会话生图） | 设计判断，学习点最值钱 |
| B-3 `schema.sql` | DB 会话写，负责人审 | 语法转写=重复劳动；但**脚本要先看后执行** |
| B-4 建库 / 入库 | DB 会话执行 | 重复操作 |
| B-5 校验 | DB 会话跑 + HP-V22 抽查 | 验证要独立于执行者 |
| C 后端骨架 | 负责人亲手做 | V1 没做过，是新技术 |
| D 完整 API | 路由样板交给 AI；规则引擎搬运负责人参与 | 一半重复、一半要懂 |
| E 前端接入 | 负责人亲手做 | `LocalStore → ApiStore` 是架构理解的关键 |
| F 测试收尾 | 测试会话独立验收 | 见 §6 |

**一句话**：V2.0 里你不再是**搬运工**（粘贴代码），你是**设计师 + 审核者**；亲手做的部分从"敲全部代码"缩减为"拍板 + 关键节点自己写"。
