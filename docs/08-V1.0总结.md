## 五、你实际掌握的概念（面试可讲）

1. **数据版本化与迁移** —— 软件升级数据结构会变，必须带版本号并能平滑迁移
2. **防御性编程** —— `null` 判空、缺字段兜底、解析失败有退路
3. **提取函数（重构）** —— 把深层嵌套拆成单一职责的小函数
4. **双向绑定** —— 界面改动即时写回状态，状态加载时回填界面
5. **加权评分（多准则决策 MCDM）** —— 把多维偏好压成一维可排序的量
6. **探索与利用（explore / exploit）** —— 多臂老虎机问题的简化形态
7. **三层降级** —— 主路径失败时逐级回退，保证永不白屏
8. **接口抽象与可替换实现** —— 同一调用点，底层实现可整体替换
9. **XSS 防护** —— 不可信文本一律 `textContent`，绝不 `innerHTML`
10. **自动化测试与独立复现** —— 纯函数可用脚本验证；报告写明"谁用什么方法验证"

## 六、做对的工程习惯

1. **先给地图再给路** —— 每个任务先说【目标】【为什么】，动手后【复盘】
2. **边界用例写进测试清单** —— 即使当时没出错，也留作将来的回归保险
3. **想法进 backlog，不阻塞当前版本** —— 判据："不做会不会导致当前版本做错"
4. **死代码清理 + 意图留存** —— 删代码前把想法写进 backlog，代码干净、想法不丢
5. **测试报告如实写明方法与分工** —— "HP 独立复现"和"负责人自测"分开标注
6. **每次改动先核实再采信** —— 不凭对话印象下结论，实际读代码

## 八、对 V2.0 的衔接

V1.0 最值钱的设计不是功能，而是**两个接口**：

```js
recommend(profile, dishes, opts)   // 挑菜的脑子 → V3.0 换成 LLM
store.load() / store.save()        // 数据存取   → V2.0 换成 HTTP API
```

**因此 V2.0 的演进路径已经确定**：只换 `store` 的实现（`LocalStore` → `ApiStore`），界面层一行不动。

**V1.0 写的每个零件在后续都有用**：
- `filterDishes` / `mergeAvoid` → 后端也照这套规则实现
- `scoreDish` → V3.0 降级链的第 2 层
- `pick()` 纯随机 → 降级链的第 3 层（永远不删）

## 九、面试怎么说（重点）

### 3 分钟版本

> 「我做了个『今天吃什么』，但它不是随机抽菜，而是**根据用户画像打分推荐**。
>
> 核心是一个**可替换的推荐接口**：V1.0 用本地规则打分（菜系、辣度、热量、心情、预算等 8 条规则加权求和），V3.0 会换成大模型，**界面层不用改**。
>
> 同时做了**三层降级**：大模型挂了退规则引擎，规则无解退纯随机，保证任何情况下都能出结果。
>
> **硬忌口是绝对约束**——本人和饭搭子的忌口都在打分之前过滤，连'惊喜推荐'分支也只能在过滤后的候选池里选。
>
> 数据层做了**版本化迁移**，用户升级不会丢数据。全程有需求/设计文档、测试报告，14 项测试全绿。」

### 可能被追问，以及怎么答

| 追问 | 回答要点 |
|---|---|
| **为什么不用豆包/DeepSeek 直接问？** | 通用模型不知道我的菜单（现实供给）、没有硬约束保证、结果不可复现不可解释。我的系统是**约束求解器**，不是知识问答器。 |
| **怎么保证不推出忌口菜？** | **先过滤、再打分**。探索分支只在过滤后的池子里选。测试里连跑 60 次采样，硬忌口零违反。 |
| **为什么用打分？** | 多准则决策：把多维偏好压成一维可排序的量。代价是不同维度的分值本来不可比，靠权重强行放到同一把尺子上——所以权重可调。 |
| **探索和利用怎么平衡？** | `exploreRate` 默认 0.15，显式分离两条策略而不是混在概率里。探索也取"新鲜菜里的最高分"，避免惊喜变惊吓。 |
| **怎么测试的？** | 逻辑层纯函数用 Node 把 `index.html` 的脚本加载进假 DOM 独立复现，UI 层手动跑。测试脚本留在 `tests/`。 |
| **这个项目的难点是什么？** | 不是写功能，是**不让任何异常路径把功能弄挂**——降级、边界、忌口约束的优先级。 |

### 一句话的差异化

> **「没有真正的原创，只有不断改进的原创。」** 这个项目从随机抽菜起步，走过规则引擎，正在走向多智能体——**演进过程本身就是我要讲的东西**。
