## 0. 三条设计原则

1. **接口先定，实现后换。** 抽象两个可替换接口 `recommend()` 与 `store()`。V1.0 用本地实现，V2.0/V3.0 换实现，**调用方一行不改**。
2. **降级不是补丁，是第一等公民。** 三层降级从第一天就写进设计，而不是等 LLM 挂了再补。
3. **不破坏现有可用性。** 现有 `pick()` 随机抽菜逻辑**一行不删**，它是永远可用的保险。

## 2. 数据模型

### 2.1 菜品模型（dish）

**v1 现状**：
```js
{ name: "麻辣烫", tags: ["川味","汤"], price: 18 }
```

**v2 目标**（`serving` 为第二版新增）：
```js
{
  id: "d_麻辣烫",              // 稳定标识（V2.0 接数据库后换成数字 id）
  name: "麻辣烫",
  tags: ["川味","汤"],          // 保留原字段，向后兼容
  price: 18,
  cuisine: "川湘",             // 菜系：川湘/江浙/粤式/北方/西北/日韩/西式/其他
  calories: 550,              // 热量 kcal（营养师核心字段，人工估算）
  spicy: 3,                   // 辣度 0-5
  heaviness: "heavy",         // 清淡 light / 适中 medium / 重口 heavy
  suitableMood: ["低落","想解压"], // 适配心情，可空数组
  serving: "single"           // 【新增】single 单人份 / share 可分享（火锅、烤肉等）
}
```

**为什么必须加 `serving`**：第二版新增的 `headcount`（人数）与 `portionSize`（饭量）**需要菜品端有对应属性才能参与打分**。如果菜品只有菜系口味标签，"4 个人吃饭"这个信息在打分表里无处安放，这两个画像字段就变成死字段——填了也没用。这是本次变更中**唯一一处必须连带改动菜品模型的地方**。

**字段缺省规则**：旧菜品没有新字段时，迁移函数按菜名关键词猜一个合理默认值（如含"沙拉"→ `calories: 180, heaviness: "light"`），猜不出来就留 `null`。
`serving` 猜不出来时**一律默认 `"single"`**（保守策略：不假设一道菜可以分享）。**不允许因为缺字段导致菜被过滤掉。**

### 2.2 用户画像（profile）

**第二版结构（12 字段，三层）**：

```js
profile = {
  // ── 画像层：我是谁、我想吃什么 ──────────────────
  hometown: "四川",           // 【拆分】家乡 → 底层口味
  currentCity: "上海",        // 【拆分】现居地 → 现实供给
  cuisine: "川湘",            // 偏好菜系（与 dish.cuisine 同枚举）
  taste: ["辣","重口"],        // 口味习惯（多选）
  goals: ["减脂"],            // 健康目标：减脂/增肌/控糖/均衡（多选）
  avoidHard: ["海鲜","内脏"],  // 绝对不吃 / 过敏（安全级硬约束，一票否决）
  avoidSoft: ["香菜","葱"],    // 不爱吃但可去（不剔除，只加提示）
  budget: 25,                // 单餐预算（元，null 表示不限）
  mood: "疲惫",               // 当前心情（单选，随时可改）

  // ── 社交层：和谁吃 ────────────────────────────
  headcount: 1,              // 【新增】用餐人数
  diningCompanions: [        // 【新增】搭子及其忌口（数组）
    { name: "小明", avoid: ["香菜"] }
  ],

  // ── 生理层：我的身体情况 ───────────────────────
  portionSize: "中",          // 【新增】饭量：小/中/大
  age: "18-25",              // 【新增】年龄段（规则引擎不参与打分）
  gender: "男"                // 【新增】性别（规则引擎不参与打分）
}
```

**⚠️ 忌口现在有两个来源**：`profile.avoid`（本人）+ `profile.diningCompanions[].avoid`（搭子）。
规则引擎**必须先把两者合并**成一个集合再做过滤，见 §6.1。**漏掉搭子忌口是本设计最容易出的 bug。**

### 2.3 localStorage 结构 v2

```js
// key: "today-eat-what:v2"
{
  version: 2,
  dishes:  [ /* dish v2 数组 */ ],
  profile: { /* profile 对象，12 字段 */ },
  history: [ "麻辣烫", "沙拉" ],   // 保留字符串数组，向后兼容
  current: { /* dish */ } | null,
  preferences: {
    mode: "random",        // "random" | "ai"
    exploreRate: 0.15      // 【新增】惊喜菜品触发概率（0~1）
  }
}
```

### 2.4 迁移策略（v1 → v2）

```
load():
  1. 读 "today-eat-what:v2" → 有且 version===2 → 直接用
  2. 否则读 "today-eat-what:v1" → 有 → migrateV1toV2(old) → 写入 v2 key
                                         ↓
                              旧 key 保留不删（回滚保险），但不影响读取
  3. 都没有 → 装载 DEFAULT_DISHES（v2 格式）+ DEFAULT_PROFILE

migrateV1toV2(old):
  - dishes：逐个补齐 cuisine/calories/spicy/heaviness/suitableMood/serving
  - history / current：原样搬运
  - profile：v1 里没有 profile，直接用 DEFAULT_PROFILE（12 字段默认值）
  - preferences：{ mode:"random", exploreRate:0.15 }
  - version: 2
```

**关于 `region` 的历史数据**：v1 的 localStorage 里根本不存在 profile 对象（只存 `{dishes, history, current}`），所以**不需要处理 `region` 的拆分迁移**——直接给默认值即可。如果将来有中间版本存过 `region`，迁移时把它**同时写入 `hometown` 和 `currentCity`** 作为兜底。

**硬性要求**：迁移函数必须能在 `try/catch` 里跑，解析失败就退回默认数据，**绝不让页面白屏**。

## 3. 接口契约（两个可替换接口）

### 3.1 `recommend()` —— 推荐引擎

```js
/**
 * 根据用户画像从候选菜品中选出最合适的一道
 * @param {Profile} profile  用户画像（12 字段，见 §2.2）
 * @param {Dish[]}  dishes   候选菜品（必须非空）
 * @param {Object}  [opts]
 *        timeoutMs   = 8000,                  // LLM 超时（V3.0 才用）
 *        mode        = "random" | "ai",
 *        history     = ["麻辣烫","沙拉"],       // 【新增】最近吃过的菜名，供探索分支使用
 *        exploreRate = 0.15                    // 【新增】惊喜菜品触发概率
 * @returns {Promise<{
 *   dish: Dish | null,
 *   reason: string,                                   // 给用户看的推荐理由
 *   source: "llm" | "rule" | "random" | "none",       // 结果来源，用于 UI 角标与调试
 *   strategy: "exploit" | "explore" | "fallback",     // 【新增】走了哪条策略分支
 *   debug?: { score: number, hits: string[] }         // 规则层的打分明细
 * }>}
 */
async function recommend(profile, dishes, opts) { /* ... */ }
```

**第二版对接口的影响（重要结论）**：
- **函数签名不变**——仍是 `(profile, dishes, opts)`，调用方一行不用改。
- `profile` 从 7 字段变成 12 字段，但**接口不关心里面有几个字段**，只多读几个键。
- `opts` 新增两个**可选**参数（`history` / `exploreRate`），不传时行为与第一版完全一致 → **向后兼容**。
- 返回值**新增一个字段** `strategy`。这是纯增量，老代码忽略它也不会坏。

> 这正是"接口先定、实现后换"的收益：一批新需求进来，接口基本没动。

**实现演进（调用方不变）**：

| 版本 | 内部实现 | `source` 取值 |
|---|---|---|
| V1.0 | 本地规则打分 | `"rule"` |
| V2.0 | 后端 `/api/recommend` | `"rule"` |
| V3.0 | LLM（经后端代理），失败回退规则 | `"llm"` / `"rule"` / `"random"` |

**契约约束（所有版本都必须满足）**：
- 返回的 `dish` **必须来自传入的 `dishes` 数组**（LLM 返回菜单外的菜名 → 视为非法结果，直接降级）。
- 任何异常都不得向上抛，必须自行降级并返回结果。
- 无法产出时返回 `{ dish: null, source: "none" }`，由 UI 决定提示文案。
- `alternatives` 为**预留字段**：V1.0 恒为 `[]`。将来要做"多推几道让用户选（3+1）"时填上即可，**不需要改接口签名**。

### 3.2 `store()` —— 数据访问层

```js
const store = {
  async load(),                 // → State（完整状态对象）
  async save(state),            // → void
  async addDish(dish),          // → State
  async removeDish(id),         // → State
  async updateProfile(patch),   // → State
  async pushHistory(name),      // → State（保留最近 8 条）
};
```

| 版本 | 实现 | 说明 |
|---|---|---|
| V1.0 | `LocalStore` | 直接操作 localStorage，含迁移逻辑 |
| V2.0 | `ApiStore` | 同签名，内部改 `fetch()`，**UI 层零改动** |

**这是"架构按未来公开设计"的落点**：V2.0 换 `store`，V3.0 换 `recommend`，两次演进都不需要动 UI 层代码。

## 4. 三层降级设计（NFR-1 落地）

```
用户点击「AI 推荐」
        │
        ▼
┌───────────────────┐  超时 8s / 网络错误 / HTTP 非 2xx / JSON 解析失败
│ ① LLM 推荐         │──────────────────────────────┐
│   source: "llm"    │                              │
└───────────────────┘                              ▼
        │ 返回菜名 ∉ 候选集                     ┌──────────────┐
        └──────────────────────────────────────▶│ ② 规则引擎    │
                                               │  source:"rule"│
                                               └──────────────┘
                                                      │ 候选集为空
                                                      │ 或全部被忌口否决
                                                      ▼
                                              ┌──────────────┐
                                              │ ③ 纯随机       │
                                              │ source:"random"│
                                              │ = 现有 pick()  │
                                              └──────────────┘
```

**UI 提示规则**：
- `source === "llm"`：正常展示 + 理由
- `source === "rule"`：展示理由，并显示角标「本地推荐」（不弹报错，不打扰用户）
- `source === "random"`：显示「已切换为随机」提示
- `source === "none"`：提示「菜单是空的，先添加几道菜」

**必须遵守**：降级过程对用户是**静默的**，不弹 alert、不显示堆栈。开发者信息只进 `console.warn`。

## 6. 规则引擎评分表（V1.0 核心逻辑）

这是 V1.0 手搓的主体，**必须由项目负责人亲手实现**。

### 6.1 硬性过滤（一票否决，优先级最高）

**忌口分两档**（v2.1 变更）：

| 档位 | 来源 | 处理 |
|---|---|---|
| **硬忌口** | `profile.avoidHard` + **所有搭子的忌口** | **直接剔除** |
| **软忌口** | `profile.avoidSoft` | **不剔除**，只在理由里加一条提示 |

| 其它条件 | 处理 |
|---|---|
| `dish.price > profile.budget`（budget 非空时） | 剔除；若剔除后候选集为空，则放宽为降权处理 |

**合并忌口的写法**（防止漏掉搭子——这是本设计最容易出的 bug）：

```js
function mergeAvoid(profile) {
  const hard = [
    ...(profile.avoidHard || []),
    // 搭子忌口一律按硬约束（保守：不确定对方是"绝对不吃"还是"可去"）
    ...(profile.diningCompanions || []).flatMap(c => c.avoid || [])
  ];
  const soft = [...(profile.avoidSoft || [])];
  return { hard, soft };
}
```

**软忌口的处理**：命中软忌口**不剔除、也不扣分**，只在 `hits` 里加一条提示文案，例如
「温馨提示：含香菜，下单可备注去掉」。

**硬忌口是绝对约束**：惊喜菜品（§6.4）、将来的 LLM 推荐（V3.0）都**不得绕过**。
正确顺序永远是：**先过滤 → 再打分 → 最后才谈探索**。

> **为什么搭子忌口一律按硬约束**：你不确定对方是"绝对不吃"还是"可去"。宁可少推荐一道，也不能给搭子推他不吃的东西——那是社交事故，代价远高于少一道菜。

> **关于"可替换"（维度的另一半，本版不做）**：区分"麻辣烫可换清汤"与"麻婆豆腐必辣"，需要**菜品端**标注"哪些属性可改"（如 `removable: ["辣"]`）。V1.0 的菜品只有 12 道、标签粗糙，标注准确性低；等 V2.0 有了数据库与 `ingredients` 表再正经做。当前用 `avoidSoft`（软忌口）已能覆盖它的主要价值。

### 6.2 加分项

| 条件 | 分值 | 计入理由文案 |
|---|---|---|
| `dish.cuisine` 与 `profile.cuisine` 一致 | +30 | 「符合你偏好的{菜系}口味」 |
| 【新增】`dish.cuisine` 与 `profile.hometown` 推断口味一致 | +25 | 「家乡菜，吃惯了的味道」 |
| 【新增】`headcount ≥ 3` 且 `dish.serving === "share"` | +25 | 「人多，适合一起分享」 |
| 目标为"减脂"且 `dish.calories ≤ 400` | +25 | 「热量较低，适合减脂」 |
| `dish.spicy` 与 `profile.taste` 含"辣"匹配（辣→spicy≥3；清淡→spicy≤1） | +20 | 「辣度符合你的口味」 |
| 目标为"增肌"且 `dish.calories ≥ 600` | +20 | 「热量充足，适合增肌」 |
| `dish.heaviness` 与 `profile.taste` 含"重口/清淡"匹配 | +15 | 「{重口/清淡}程度合适」 |
| `dish.suitableMood` 包含 `profile.mood` | +15 | 「适合你现在的{mood}状态」 |
| 【新增】`dish.cuisine` 与 `profile.currentCity` 主流供给一致 | +10 | 「你那边常见的选择」 |
| 【新增】`headcount === 1` 且 `dish.serving === "single"` | +10 | 「一个人的份量刚好」 |
| 【新增】`portionSize` 与 `dish.calories` 匹配（小→≤350；中→350~650；大→≥650） | +10 | 「份量符合你的饭量」 |
| `dish.tags` 与 `profile.taste` 有交集 | +10 / 每项（上限 20） | 「口味标签匹配」 |
| `dish.price ≤ profile.budget * 0.8` | +5 | 「价格实惠」 |

**`age` / `gender` 刻意不在上表中**——理由见需求文档 §3.3，它们没有可靠的规则依据，只作为 V3.0 的 LLM 上下文。

**关于 hometown 的作用**：地域本身不直接对应菜系，需要一张映射表把「四川」翻译成「川湘」（见 §6.5）。用户手动选的 `cuisine` 优先级更高（+30 > +25）——**主动声明优先于地址推断**。

### 6.3 选取与理由

```
1. 按总分降序排序
2. 取最高分；若最高分并列 ≥ 2 道 → 在其中随机取一道（保留随机性）
3. reason = 命中的前 2~3 条加分项文案拼接；一条都没命中时
   reason = "随机为你挑选，试试新口味"
```

**没有偏好设置时（profile 全空）**：所有菜得分为 0 → 退化为随机选，行为与现有 `pick()` 一致。**这是设计上的正确行为，不是 bug。**

### 6.4 探索与利用：惊喜菜品（第二版新增）

**设计目标**：把"推荐你爱吃的"（利用 / exploit）和"帮你换换口味"（探索 / explore）**显式分离**，而不是混在概率里糊过去。

```
recommend(profile, dishes, { history, exploreRate })

第 1 步 · 硬性过滤（§6.1）→ 得到候选池 P
         ⚠️ 惊喜菜品只在 P 内部探索，绝不越过忌口
第 2 步 · 掷骰子：Math.random() < exploreRate ?
         ├─ 否 → 走"利用"：取最高分（§6.3），strategy: "exploit"
         └─ 是 → 走"探索"，strategy: "explore"
                 a. 从 P 中剔除 history 里出现过的菜（最近吃过的）
                 b. 若剔除后为空 → 退回"利用"分支，strategy 改回 "exploit"
                 c. 在剩余池中取"分数中上但历史出现最少"的一道
第 3 步 · 返回结果，strategy 标明走了哪条分支
```

**约束**：
- `exploreRate` 默认 `0.15`，存在 `preferences.exploreRate`，用户可调。
- 探索分支产出的菜**仍必须来自硬性过滤后的候选池 P**。
- 探索分支的 `reason` 必须与利用分支**文案不同**，让用户知道"这是在给你换口味"，例如：
  「换换口味：你有段时间没吃这个了」。

**为什么这样设计**：如果只在最高分附近抖动，用户永远吃不到"从没点过但可能喜欢"的菜；如果随机范围太大，又会推出明显不合口味的菜。显式分离之后，这个权衡变成一个**可以调的参数**，而不是玄学。

## 7. 数据库表设计（V2.0 预备，本次不实现）

规范到第三范式，保留"多对多标签表"这一教学重点。

```sql
-- 用户表（V2.0 不实现登录，但表先建好，为公开做准备）
CREATE TABLE users (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  username    VARCHAR(50) UNIQUE NOT NULL,
  created_at  DATETIME DEFAULT CURRENT_TIMESTAMP
);

-- 菜品表
CREATE TABLE dishes (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  name        VARCHAR(50) NOT NULL UNIQUE,
  price       DECIMAL(6,2),
  calories    INT,                                   -- 热量 kcal
  spicy       TINYINT CHECK (spicy BETWEEN 0 AND 5),
  heaviness   VARCHAR(10) CHECK (heaviness IN ('light','medium','heavy')),
  serving     VARCHAR(10) DEFAULT 'single'           -- 【第二版新增】single|share
              CHECK (serving IN ('single','share')),
  created_at  DATETIME DEFAULT CURRENT_TIMESTAMP
);

-- 标签表（一张表统管：菜系/口味/健康/心情/食材/忌口）
CREATE TABLE tags (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  name        VARCHAR(20) NOT NULL,
  category    VARCHAR(20) NOT NULL,   -- cuisine|taste|health|mood|ingredient
  UNIQUE (name, category)
);

-- 菜品 ⇄ 标签：多对多
CREATE TABLE dish_tags (
  dish_id     INT NOT NULL,
  tag_id      INT NOT NULL,
  PRIMARY KEY (dish_id, tag_id),
  FOREIGN KEY (dish_id) REFERENCES dishes(id) ON DELETE CASCADE,
  FOREIGN KEY (tag_id)  REFERENCES tags(id)   ON DELETE CASCADE
);

-- 用户偏好（一对一）：画像层 + 生理层都落在这一张表
CREATE TABLE user_profiles (
  user_id       INT PRIMARY KEY,
  hometown      VARCHAR(20),                        -- 【第二版拆分】家乡（底层口味）
  current_city  VARCHAR(20),                        -- 【第二版拆分】现居地（现实供给）
  budget        DECIMAL(6,2),
  mood          VARCHAR(20),
  headcount     TINYINT DEFAULT 1,                  -- 【第二版新增】用餐人数
  portion_size  VARCHAR(5),                         -- 【第二版新增】饭量：小/中/大
  age_range     VARCHAR(10),                        -- 【第二版新增】年龄段（不参与规则打分）
  gender        VARCHAR(10),                        -- 【第二版新增】性别（不参与规则打分）
  updated_at    DATETIME DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
);

-- 【第二版新增】搭子表：一次用餐可能有多人，每人有各自的忌口
-- 单独建表而不是塞进 user_profiles 的字段，因为这是「一对多」关系
CREATE TABLE dining_companions (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id     INT NOT NULL,                         -- 这是谁的搭子
  name        VARCHAR(30) NOT NULL,                 -- 搭子称呼，如「小明」
  FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
);

-- 【第二版新增】搭子忌口（多对多）：小明不吃香菜、不吃内脏 → 两行
CREATE TABLE companion_avoid_tags (
  companion_id INT NOT NULL,
  tag_id       INT NOT NULL,
  PRIMARY KEY (companion_id, tag_id),
  FOREIGN KEY (companion_id) REFERENCES dining_companions(id) ON DELETE CASCADE,
  FOREIGN KEY (tag_id)       REFERENCES tags(id)              ON DELETE CASCADE
);

-- 用户偏好标签（多对多 + 用途区分）：口味/健康目标/忌口 共用
CREATE TABLE user_preference_tags (
  user_id     INT NOT NULL,
  tag_id      INT NOT NULL,
  kind        VARCHAR(10) NOT NULL,   -- taste|goal|avoid_hard|avoid_soft
  PRIMARY KEY (user_id, tag_id, kind),
  FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE,
  FOREIGN KEY (tag_id)  REFERENCES tags(id)  ON DELETE CASCADE
);

-- 抽取历史（record 每次推荐，含来源与策略，便于后续分析）
-- 这张表同时是 V3.0「长期记忆」的数据基础
CREATE TABLE pick_history (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id     INT,
  dish_id     INT,
  source      VARCHAR(10),            -- llm|rule|random
  strategy    VARCHAR(10),            -- 【第二版新增】exploit|explore|fallback
  reason      TEXT,
  created_at  DATETIME DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (user_id) REFERENCES users(id),
  FOREIGN KEY (dish_id) REFERENCES dishes(id)
);
```

**表数量**：原文写「共 **8 张**」，**计数有误**——上面 SQL 块里本来就是 **9 张**；经 §7.1 的 B 阶段决策后再加 `dish_options` → **共 10 张**。

**第二版新增表的设计理由**：搭子忌口单独建两张表而不是塞一个字符串字段，原因是它在数据库里是标准的**一对多 + 多对多**关系（一个用户有多个搭子，一个搭子有多个忌口）。这正是"亲手设计表结构"最该练的部分——也是面试里最容易讲清楚的设计点。

**下一步建议**：V2.0 时把这份表结构在 **SQLyog**（你机器上已经装好了）里**亲手画一遍 ER 图**再建库——这是"亲手设计数据库"的核心价值，别直接复制粘贴执行。

**要点**：`tags` 表不分家（不建 5 张标签表），靠 `category` 区分。这是规范化的常见做法，也是面试可讲的点。

### 7.1 V2-B 表设计修订（2026-10-13 · HP-V22）

> 本节是 B 阶段的**契约变更记录**，B-3 写 `schema.sql` 时**以本节的表清单与语义为准**。
> 修订依据：`04-想法收集箱.md` 第 1 / 2 / 3 条（属性的可变性）+ 2026-10-13 负责人提出的**用餐时段维度**。

**决策 1 · 属性的可变性进关联表 → 新增 `dish_options`（第 10 张表）**

语义：**一行 = 「某道菜 × 某个可调属性 × 一个可选取值」**。
规则：**在 `dish_options` 里有行 = 该属性可调；没有行 = 固定不可调**——
所以**不需要单独的 `is_removable` 字段**：麻婆豆腐没有 `spicy_level` 行，这本身就是「必辣」的表达。

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | INT AI PK | |
| `dish_id` | INT FK → `dishes.id` | |
| `option_name` | VARCHAR(20) | `spicy_level` / `soup_base` / `cilantro` / `portion` |
| `option_value` | VARCHAR(20) | 中辣 / 清汤 / 免香菜 / 大份 |
| `is_default` | TINYINT(1) DEFAULT 0 | 默认取值 |
| `extra_price` | DECIMAL(6,2) DEFAULT 0 | 加料加价，通常 0 |
| 约束 | `UNIQUE (dish_id, option_name, option_value)` | 防重复 |

> **待定（B-2 画图时定）**：`option_value` 存文本，还是外键指向 `tags.id`。HP 倾向存文本。

**决策 2 · 辣度分两处**
`dishes.spicy`（TINYINT 0–5）= **基础辣度**，永远有值（不辣的菜为 0）；
辣度「能不能改、能改成几档」= `dish_options` 里 `option_name='spicy_level'` 的那些行。

**决策 3 · 价格不进模型**
`dishes.price` 保持静态参考价；地域浮动不做（`04` 第 4 条）。

**决策 4 · 用餐时段用 `tags` 的 `meal` 类目，`dishes` 不加字段**
- `tags.category` 取值扩为：`cuisine | taste | health | mood | ingredient | meal`
- 5 个 meal 标签：**早餐 / 午餐 / 晚餐 / 下午茶 / 夜宵**
- 一道菜适合多餐 = `dish_tags` 多行；**不标 = 不限时段**（如白米饭）

**决策 5 · `user_profiles` 增加 `meal_period`**
`VARCHAR(10)`，与 `mood` **同级**——都是「本次可改」的上下文，不是长期偏好。
长期偏好（如「从不吃早餐」）按 YAGNI 暂不建，将来走 `user_preference_tags` 的 `kind='meal'`。

**决策 6 · 建表脚本的语法转写要求（B-3 必读，复制粘贴会报错）**

| §7 原文（SQLite） | MySQL 8 写法 |
|---|---|
| `INTEGER PRIMARY KEY AUTOINCREMENT` | `INT NOT NULL AUTO_INCREMENT PRIMARY KEY` |
| 无字符集声明 | 每张表加 `ENGINE=InnoDB DEFAULT CHARSET=utf8mb4` |
| `TINYINT CHECK (...)` | 保留 CHECK（MySQL 8.0.16+ 才生效） |
| `pick_history` 缺主键 | 补 `id INT NOT NULL AUTO_INCREMENT PRIMARY KEY` |

**决策 7 · 连带的设计改动（V2-D 执行，本次只记录）**
`§6.2 加分项` 需增一条**时段匹配**规则：`profile.meal_period` ∈ 该菜的 meal 标签 → 加分。

**V2-B 的 10 张表清单**：`users` / `dishes` / `tags` / `dish_tags` / `dish_options` / `user_profiles` / `dining_companions` / `companion_avoid_tags` / `user_preference_tags` / `pick_history`
