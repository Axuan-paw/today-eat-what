## 0. 一句话定义

把「点一下随机抽菜」升级成**会根据你的家乡口味、现居供给、健康目标、同行搭子和当下心情给出推荐、并说明理由**的私人营养师助手；**任何情况下都必须能抽出一道菜，且任何情况下都不能推出你或搭子忌口的菜**。

## 1. 项目定位与演进目标

| 阶段 | 名称 | 交付物 | 目的 |
|---|---|---|---|
| V1.0 | 偏好画像 + 规则推荐 | 纯前端单页，本地规则打分 | 亲手体会「数据输入 → 过滤 → 输出」的基础逻辑 |
| V2.0 | 全栈 + 数据库 | FastAPI 后端 + SQLite/MySQL + REST API | 亲手设计表结构、完成前后端联调 |
| V3.0 | LLM + MAS 完全体 | 多模态大模型 + 多 Agent 协作 | 对接考研关键词（LLM / MAS / CAS）与就业 |

**战略定位**：本项目的演进过程本身就是「单智能体 → 多智能体」的载体，为考研复试提供可讲述的完整故事，为就业提供第一份真实全栈履历。

**核心理念**：没有真正的原创，只有不断改进的原创。本项目的"小创新"落在四处：
1. **推荐引擎可替换**：同一调用点，V1.0 用规则、V3.0 用 LLM（降级天然成立）。
2. **约束求解式 LLM**：不让模型自由发挥菜名，只在候选集内选择并输出结构化理由，结果可被程序校验。
3. **探索与利用的显式分离**：把"推荐你爱吃的"和"帮你换换口味"做成两套并存的策略，而不是混在一起靠概率糊过去。
4. **可用性优先**：LLM 是增强项而非依赖项，断网、超时、额度耗尽都不影响基本功能。

### 1.1 产品形态演进（第二版补充）

| 阶段 | 形态 | 说明 |
|---|---|---|
| **V1.0（当前）** | **自用 + 全量展示** | 因为是自用，不追求简化：14 个画像字段一次做全，界面上全部可见可改，便于观察每个字段对推荐的实际影响 |
| **未来上线** | **默认设置 + 长期记忆 + 自然语言输入** | 面向他人时必须降低配置负担：开箱即用的默认画像、系统自动记住长期偏好、用一句话（"今天想和室友吃点清淡的"）代替填表单 |
| **项目定位** | **开源** | 代码公开；是否上线与商业化视后续情况再定，当前不作为目标 |

> **对设计的硬约束（重要）**：V1.0 的"全量展示"**不能**变成未来"必须堆更多表单"的理由。
> 因此数据结构必须**可被 LLM 直接理解**——存储的是结构化字段（`hometown: "四川"`），而不是 UI 控件的状态。
> 这样未来换成自然语言输入时，只需把一句话解析成同一套结构，界面可以整个重写而数据层不动。
> 设计文档 §7 的 `pick_history` 表就是为"长期记忆"预留的。

## 3. 用户画像需求（数据输入层）

这是 LLM 推荐的**输入数据**，也是 V1.0 的核心交付。

> **第二版变更**：画像字段从 7 个扩展为 **14 个**，按「画像层 / 社交层 / 生理层」三层组织。
> `region` 拆分为 `hometown`（家乡，底层口味）与 `currentCity`（现居地，现实供给）。

### 3.1 画像层（我是谁、我想吃什么）

| 字段 | 含义 | 类型 | 取值示例 | 影响 |
|---|---|---|---|---|
| `hometown` | 家乡（**底层口味**） | 单选 | 四川 / 湖南 / 上海 / 广东 / 北京 / 其他 | 推断"吃惯了"的口味倾向，是味觉底色 |
| `currentCity` | 现居地（**现实供给**） | 单选 | 同上 | 推断实际上能吃到什么（外卖/堂食供给） |
| `cuisine` | 偏好菜系 | 单选 | 川湘 / 江浙 / 粤式 / 北方 / 西北 / 日韩 / 西式 / 不限 | 直接加分项 |
| `taste` | 口味习惯 | 多选 | 辣 / 清淡 / 重口 / 酸甜 / 鲜 | 与菜品属性匹配 |
| `goals` | 健康目标 | 多选 | 减脂 / 增肌 / 控糖 / 均衡 | 决定热量与营养倾向 |
| `avoidHard` | **本人绝不吃 / 过敏** | 多选（可自定义） | 海鲜 / 内脏 / 花生 | **一票否决**（安全级，任何策略不可绕过） |
| `avoidSoft` | **本人不爱吃但可去** | 多选（可自定义） | 香菜 / 葱 / 蒜 | 不剔除，只在理由里提示「可备注去掉」 |
| `budget` | 单餐预算 | 数值（元） | 25 | 超预算降权 |
| `mood` | 当前心情 | 单选（每次可改） | 开心 / 疲惫 / 低落 / 想解压 / 没胃口 / 想犒劳自己 | 匹配菜品情绪标签 |

**为什么 hometown 和 currentCity 必须分开**：这两者经常冲突。一个四川人在上海，底层口味想吃辣，但上海的供给里清淡菜更多。分开之后，"我想吃什么"和"我能吃到什么"是两个独立信号，不会被一个字段平均掉。

**为什么忌口要分两档（v2.1 新增）**：
把"过敏/绝不吃"和"不爱吃但可去"混成一个字段，会导致两种错误——要么把"不爱吃香菜"当成绝对禁令，把好菜全过滤掉；要么把"海鲜过敏"当成可以商量，推出危险建议。
分层之后：

- `avoidHard`（过敏 / 绝对不吃）→ **一票否决**，任何策略（含惊喜菜品）都不可绕过
- `avoidSoft`（不爱吃但可去）→ **不剔除**，只在推荐理由里提示「可备注去掉」

> 这是项目负责人提出的产品设计，WP 建议的落地方式：V1.0 先用「两个输入框 + 两个分支」实现；菜品端的「可替换标注」（麻辣烫可换清汤 vs 麻婆豆腐必辣）留到 V2.0 用数据库正经做。

### 3.2 社交层（和谁吃）

| 字段 | 含义 | 类型 | 取值示例 | 影响 |
|---|---|---|---|---|
| `headcount` | 用餐人数 | 数值（≥1） | 1 / 2 / 4 | 人数多 → 倾向可分享的菜（火锅、烤肉） |
| `diningCompanions` | 搭子及各自忌口 | 数组 | `[{name:"小明", avoid:["香菜"]}]` | **搭子忌口同样一票否决** |

**注意**：`diningCompanions` 是**数组**而非单值。可能同时和多人吃饭，每个人的忌口要分别记录，理由展示时也需要点名（"因为小明不吃香菜"）。

### 3.3 生理层（我的身体情况）

| 字段 | 含义 | 类型 | 取值示例 | 影响 |
|---|---|---|---|---|
| `portionSize` | 饭量 | 单选 | 小 / 中 / 大 | 影响份量与菜品类型 |
| `age` | 年龄段 | 单选 | 18以下 / 18-25 / 26-35 / 36-50 / 50以上 | 影响热量区间（**弱**） |
| `gender` | 性别 | 单选 | 男 / 女 / 不愿透露 | **规则引擎中不参与打分**，仅作 LLM 上下文 |

> **重要设计判断（HP 给出，请知悉）**：`age` 与 `gender` 在**纯规则引擎里几乎无法产生可靠打分**——年龄和性别推不出你想吃什么。它们的真实价值是 V3.0 交给 LLM 时的上下文（模型能从大量语料里学到"25 岁男性减脂"这类模糊关联）。
> 因此 V1.0 **只做存储与展示，不做打分**。这不是偷懒，而是避免做出一个"看起来智能、实际是噪音"的系统。

**验收要求**：以上 **14 个字段**必须能在界面上修改、写入 localStorage、刷新后不丢。

**任何情况下，"惊喜"都不能成为推出忌口菜品的理由。**

## 5. 非功能需求（本项目的重点）

| 编号 | 需求 | 说明 |
|---|---|---|
| NFR-1 | **永不白屏** | LLM 调用失败/超时/返回非法 → 自动降级到规则 → 再降级到随机。见设计文档第 4 节 |
| NFR-2 | **API Key 绝不进 git** | key 只允许存在于 `config.local.js`（已进 .gitignore）或服务端环境变量；仓库内只保留 `config.example.js` 模板 |
| NFR-3 | **XSS 防护** | 所有 LLM 返回文本、用户输入在插入 DOM 前必须过 `esc()` |
| NFR-4 | **数据可迁移** | localStorage 结构带 `version` 字段，升级时必须写迁移函数 |
| NFR-5 | **离线可用** | 断网状态下打开页面，随机抽菜功能完全正常 |
| NFR-6 | **响应时间** | LLM 调用超过 8 秒视为超时并降级；界面在此期间必须有加载态 |
| NFR-7 | **零构建** | V1.0 不使用任何构建工具，双击 HTML（经静态服务器）即可运行 |
| NFR-8 | **忌口不可违反** | 忌口（本人 + 搭子）是**绝对约束**，任何策略分支（含惊喜菜品）都不得绕过。见 FR-8 |

## 6. 明确不做的事（Non-Goals）

- ❌ V1.0 不做用户注册/登录（V2.0 预留 `users` 表，但不实现鉴权）
- ❌ V1.0 不引入任何前端框架（React/Vue）
- ❌ V1.0 不引入 npm 依赖（保持零构建）
- ❌ 不做真实营养学计算（热量为人工估算值，够用即可）
- ❌ 不做支付、外卖下单对接
- ❌ 不追求 UI 动画复杂度
- ❌ **V1.0 不实现自然语言输入与长期记忆**（属 V3.0，但数据结构需为其预留，见 §1.1）
- ❌ **不基于 `age` / `gender` 做规则打分**（无可靠依据，见 §3.3）

## 7. 验收标准（V1.0 整体）

1. 断网状态下刷新页面，点「抽一个」能正常滚出菜名。
2. 设置家乡=四川、菜系=川湘、口味=辣、目标=减脂、忌口=香菜 后点「AI 推荐」，返回的菜**不含香菜**、**菜系为川湘**、**热量在合理区间**，并显示理由。
3. 手动清空 localStorage 后刷新，页面自动装载 12 道默认菜且 `version` 为 2。
4. 浏览器控制台执行 `localStorage.getItem('today-eat-what:v1')` 有旧数据时，升级后旧菜品**一道不少**（同名菜保留原有价格）。
5. 搜索框输入 `辣`，能过滤出带该标签的菜。
6. `git status` 中**不出现任何含 key 的文件**；`git log -p` 中搜不到 `sk-` 开头的字符串。
7. **搭子忌口生效**：添加搭子"小明，忌口香菜"，连点 20 次推荐，结果**永远不含香菜**。
8. **惊喜菜品不越界**：触发惊喜推荐时，结果仍不包含本人或搭子的任何忌口。
9. **人数影响结果**：设置人数=4 时，推荐结果明显倾向 `serving = "share"` 的菜品。
10. **画像字段全部可持久化**：改完所有画像字段后刷新，值全部保留（含搭子）。
11. **软忌口不剔除**：把「香菜」填进 `avoidSoft`（不爱吃可去），连点 20 次推荐——**允许出现含香菜的菜**，但理由里必须带「可备注去掉」的提示。
12. **硬忌口不计情面**：把「海鲜」填进 `avoidHard`，含海鲜的菜在 20 次推荐中**一次都不能出现**。

## 8. 风险与待确认项

| 风险 | 影响 | 应对 |
|---|---|---|
| DeepSeek API 的浏览器跨域（CORS）行为未验证 | 纯前端直连方案可能根本跑不通 | 由负责人在浏览器实测；若被拒则 V3.0 直接上后端代理，V1.0 不受影响 |
| 本机网络对 api.deepseek.com 不通 | 无法联调 LLM | 已有三层降级，不阻塞 V1.0；机器上已装 Ollama，可考虑本地模型替代 |
| 画像字段增至 14 个，V1.0 界面变复杂 | 手搓工作量上升（T3 约 +1h） | 已按三层分组展示；若负担过重，可协商把生理层降级为 V1.5 |
| `age` / `gender` 无法参与规则打分 | 用户可能期望它们生效 | 已在 §3.3 明确说明；其价值在 V3.0 的 LLM 上下文 |
| `headcount` / `portionSize` 依赖菜品端 `serving` 字段 | 菜品未标注则这两个字段失效 | FR-2 已纳入 `serving`；默认 12 道菜需补标 |
| 项目负责人精力分散（同时开多个会话） | 上下文混乱、改同一文件冲突 | 并行会话 ≤ 2；同一文件同一时间只有一个会话在改 |
| API Key 泄露 | 他人盗用额度 | NFR-2 + 提交前检查清单 |
| 现有 localStorage 有本人数据 | 升级丢数据 | FR-6 强制迁移 + 验收标准 4 |
